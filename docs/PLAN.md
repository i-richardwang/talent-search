# 实施方案

本文定义当前产品的技术边界、数据模型、ETL 规则、检索语义和界面结构。产品目标与范围见 [PROJECT.md](PROJECT.md)。

## 1. 技术边界

- Web：TanStack Start、React 19、Tailwind CSS 4、Kumo；
- 数据库：Postgres、Drizzle ORM；
- 数据加工：Python、pandas、pyarrow、psycopg；
- 代码质量：Biome、TypeScript、Node test runner；
- 表结构只由 `src/db/schema.ts` 定义，通过 `npm run db:push` 同步；
- Python ETL 只读取源数据并写入现有表，不创建或修改表结构；
- Python 版本与依赖由 `pyproject.toml` 和 `uv.lock` 固定；
- 页面只通过 `src/server/functions.ts` 访问数据库。

目录职责：

```text
etl/contract.py              源契约：适配器要交出的三张表
etl/pipeline.py              通用切段、校验与派生
etl/sources/                 数据源适配器（默认不进版本库）
etl/load.py                  批量写库
src/db/                      schema 与数据库连接
src/search/                  查询解析、匹配、分面、结果契约
src/server/                  服务端函数边界与查询记录
src/lib/                     跨层纯函数
src/components/              跨路由 React 组件
src/routes/                  零态、搜索工作台及其共用组件与状态
tests/                       单元测试、渲染测试、真 SQL 集成测试
```

## 2. 数据流

ETL 在**数据源**与**管线**之间只有一份契约（`etl/contract.py`）。适配器把某一套人事数据翻译成三张摊平的表，管线之后的每一步都与数据从哪来无关：

| 契约表 | 内容 | 谁决定 |
|---|---|---|
| `employees` | 人群与档案：工号、姓名、入职日、学历、学校、招聘来源 | 适配器（**谁在这张表里谁就进库**） |
| `assignments` | 组织内任职段：起止、部门、部门路径、岗位、职级、序列三级、段身份 | 适配器（切段规则） |
| `external` | 入职前经历：起止、公司、岗位、描述、公司属性、待业标记 | 适配器 |

```text
人事数据（parquet / CSV / 接口）
       │
       ▼
etl/sources/<name>.py   适配器：字段名、字典码、人群口径都在这一层
       │  SourceData（etl/contract.py）
       ▼
etl/pipeline.py         区间校验、封口、相邻段合并、时长与当前信息派生
       │
       ▼
etl/load.py ──COPY──▶ employee / experience
```

这条缝的位置是这样定的：**凡是「换一套数据就得重写」的，归适配器；凡是「换一套数据也必须成立」的，归管线。**不变量只写一遍，接第二个数据源时才不会长出第二套「什么算一段经历」。

适配器默认不进版本库：表名、字段名、字典码、人群口径本身就是一家组织的内部信息。仓库里只保留 `csv_dir` 这一份参考实现——它的列名就是契约本身，因此同时是契约的可执行说明和最省事的接入方式。

真实员工数据不得进入版本库；重建采用 truncate + COPY，整批结果保持自洽。

## 3. 数据模型

### employee

一人一行，只保存当前检索结果或详情页会读取的字段：

- 身份：`emp_id`、`name`；
- 当前状态：`cur_dept`、`cur_title`、`cur_seq_l1/l2/l3`、`cur_level`；
- 档案信息：`hire_date`、`education_level`、`school`、`recruitment`。

`org_id`、`job_code` 等切段工作值只在 ETL 内存在，计算完成后丢弃。员工按主键读取，当前没有姓名模糊检索或当前序列查询，因此不为这两条不存在的路径保留索引。

### experience

一段经历一行，公司内经历与入职前经历使用同一结构：

| 字段 | 公司内 | 入职前 |
|---|---|---|
| `kind` | `internal` | `external` |
| `start_date` / `end_date` | 异动有效期 | 工作经历起止 |
| `org` | 末级部门 | 公司名 |
| `org_path` | 完整部门路径 | 空 |
| `org_meta` | 空 | `company_tag` / `industry` / `nature` |
| `title` | 岗位名 | 入职前岗位名 |
| `seq_l1/l2/l3` | 序列 | 空 |
| `level` | 职级 | 空 |
| `description` | 空 | 简历中的职责描述 |
| `months` | 计算时长 | 计算时长 |

数据库强制以下不变量：

- `kind` 只能是 `internal` 或 `external`；
- `months` 必须大于 0；
- `end_date` 为空或不早于 `start_date`；
- `emp_id` 必须引用存在的员工。

岗位、组织、序列和描述保留原始表达，当前检索直接使用这些字段，不建立没有读者的派生标签层。

### 索引

- `(experience.emp_id, experience.start_date)`：个人时间线；
- `(experience.seq_l1, experience.seq_l2)`：序列等值筛选；
- `seq_l1 / seq_l2 / seq_l3 / title / org / org_path / description` 各自的 `gin_trgm_ops`：中文子串检索。

七个可检索字段会组成 OR；缺少任意一个 trigram 索引都会使整条命中判定退化为顺序扫描。两字中文无法形成 trigram，只能顺序扫描，这是当前检索方式的性能下限。

## 4. ETL 规则

### 管线（对所有数据源生效）

1. 人群以 `employees` 为准，经历表里指向库外的人一律丢弃；
2. 没有开始日期、生效日在未来、结束早于开始的段一律**拒绝导入并报出数量**，不猜日期，也不靠 `max(1, ...)` 把错误区间伪装成一月经历；
3. 组织内经历的末段 `end_date` 为空表示至今，时长统一计算到本批次的 `as_of`；
4. 入职前经历缺少结束日期时用该员工入职日封口，无入职日则拒绝导入；
5. `segment_key` 相同的相邻段合并为一段，并按合并后的区间重算时长；
6. 待业段保留，岗位显示为「待业」，不接描述——它解释履历上的空档，但不是一段可检索的经历；
7. 公司属性只保存非空的 `company_tag`、`industry`、`nature`，三项全空写 NULL 而不是 `{}`；
8. `cur_*` 一律从最后一段组织内经历派生，不从源的快照里另取一份——否则库里会有两个「他现在在哪」。

所有日期与时长在写库前计算，数据库约束负责阻止其他入口写入非法经历。

### 适配器（每套数据自己决定）

人群口径、字段映射、字典码翻译、切段规则、序列归一、描述对齐，以及上游系统的已知缺陷（截断、脏 JSON、重叠区间）。

`segment_key` 是适配器交给管线的唯一一个判断题：**这两段相邻的段是不是同一件事。**源系统里部门被重新登记、或一次异动被拆成两条时会切出内容相同的相邻段，它们不是两段经历；而判据只有源自己知道（组织 id + job code 比中文名可靠）。没有更好的东西时，填「部门 + 岗位」也是成立的。

## 5. 检索语义

### 查询解析

查询被解析成概念词，每个词有独立模式：

- 必须：默认模式，多个必须词在人级别采用 AND；
- 加分：不参与准入，只提升已命中候选人的排名；
- 排除：命中者从结果、总数和分面中一并剔除；
- 停用：保留词和原模式，本次检索不参与任何计算。

`parseChips` 是全站唯一解析入口，`parseChips(toQuery(chips))` 必须保持往返一致；
查询串（`渠道运营,+带团队,-实习,~管理`）是这组条件的规范写法，存在 `search_turn.chips`
里，不出现在 URL 上。

### 查询记录

一次「我要找什么人」落成 `search_turn` 的一行，URL 是 `/s/:turnId`：

| 列 | 读者 |
|---|---|
| `raw_text` | 「重新理解」的输入；最近搜索的标题 |
| `chips` | 这次检索的条件。`null` 表示还没理解——整句提交先落记录再理解 |
| `filters` | 模型认出的筛选，理解后一次性播进 URL |
| `degraded` | 退回了规则解析，界面必须说出来 |
| `parent_turn_id` / `root_turn_id` | 派生链；最近搜索按 root 去重 |

记录不可变，改查询一律派生新记录（push 导航，所以后退键就是撤销）。唯一的可变位是
把 `chips` 从 `null` 补成理解结果，`update ... where chips is null` 保证只补一次。

数据库强制以下不变量：

- 一条记录必须有 `raw_text` 或 `chips` 之一，两者全空的记录不存在；
- `root_turn_id` 必须指向一条真实存在的记录；
- `(parent_turn_id, root_turn_id)` 必须指向 `(id, root_turn_id)`——父记录存在，
  且派生记录与父记录同属一条链。链头的 `parent_turn_id` 为空，复合外键不检查。

「只 INSERT」没有库级约束，由应用代码保证。

这样做换来三件用 URL 存查询做不到的事：原话留得住所以能重新理解；同一个
`/s/:id` 必然是同一批人，因为记录不可变而不是因为凑巧没人再调模型；
改条件（模型判成必须、人改成加分）自己留在库里，那是这个产品唯一能产出的
模型评估数据。

### 中文匹配

Postgres 的 `to_tsvector` 不对中文切词，`pg_trgm` 相似度也不能提供可靠的中文语义相似度，因此当前统一使用转义后的 `ILIKE '%词%'`。

整词没有命中时，系统从长到短探测该词的子串，选择语料中真实存在的最长形态。探测只依赖查询和完整语料，不受当前筛选影响；实际使用的子串会显示在对应查询条件上。

### 多路打分

一个词对一段经历同时检查四路，取权重最高的一路：

| 路 | 字段 | 权重 |
|---|---|---|
| `seq` | `seq_l1/l2/l3` | 1.0 |
| `title` | `title` | 1.0 |
| `org` | `org` / `org_path` | 0.5 |
| `description` | `description` | 0.25 |

一个概念词对一个人的分数由三个有界因子相乘：

```text
词分 = 强度（最硬的一路的权重）× 时长 × 近因
时长 = 0.8 + 0.2 × 累计月数 / (累计月数 + 48)
近因 = 0.7 + 0.3 × 36 / (36 + 距今月数)
```

强度取该人所有命中段里最高的一路；时长与近因只统计**最硬那一路**的段——拿简历里提过一句的段去给序列命中续时长，是把两档证据混成一份。

两个地板的乘积（0.56）必须大于相邻路权重的最小比值（0.5），时长与近因因此只决定同一档证据内部的先后，永远不会让部门命中反超序列命中。

必须词分数相乘；加分词命中时乘以 `1 + 0.5 × 词分`，未命中不产生因子。常量统一定义在 `src/search/weights.ts`，求值在 `src/search/rank.ts`（纯函数，不碰数据库）。

### 查询理解

整句话提交时，先把它翻译成一组带强度的条件。没配 `LLM_BASE_URL` 或模型调用失败时，退回确定性的本地规则解析（`parseChips`），并把 `degraded` 记在这条查询记录上——规则解析读不出语气，「最好」「不要」会被一律判成必须条件，界面必须说出来并给出「重新理解」。

**理解不挡在导航前面。** 提交只落一条记录（一次 INSERT），页面立刻进入工作台，模型那一跳在结果将要出现的位置就地完成。模型单次可以从一秒跳到几十秒，让它挡在零态和工作台之间，表现就是首页卡住。

- 调用只发生在 `src/server/llm.ts`，走 OpenAI 兼容端点，换模型只改环境变量；
- 输出形状由 `intentSchema` 约束（进 `response_format: json_schema`），回来之后再过 `toIntent` 收窄，两道各有各的职责；
- 公司档的取值从语料里取（`companyTags()`），模型只能从库里真有的档里挑，不许凭常识造词；
- 序列不做成筛选：它本来就是权重最高的一路，写成概念词照样命中，还多两路召回；
- 每个词过一遍 `parseQuery`，保证与手敲的词走同一条路，URL 往返无损；
- **发出去的只有用户那句话和公司档取值**，不含任何个人数据。

结果落在已有的 chips 上，用户看得见、改得动、删得掉——这是它能安全接进主链路的全部原因。

### 结果与分面

`search(query, filters, limit)` 返回：

- `terms`：参与结果展示的概念词与实际检索形态；
- `results`：按相关度排序的员工、逐词聚合的排名依据，以及时间线使用的原始命中证据；
- `facets`：各筛选项选中后剩余的人数；
- `total`：截断前的总人数。

分面与排名不是「共用同一语义」，而是对**同一份事实**做不同的分组，口径分家在结构上不可能发生。计算某一维分面时只移除该维自己的筛选，其余筛选继续生效。

分页通过增加 `limit` 重新取得前 N 名，不使用 offset。默认 50 人，最多 500 人；界面始终说明已显示人数、总人数、排序依据和无法继续加载的原因。

## 6. Web 结构

- `/`：零态。语料概览、词汇表、示例与最近搜索；
- `/s/:turnId`：搜索工作台。路径指向一条查询记录，query string 只带视图状态
  （五个筛选维度 + 翻页数）；
- `/s/:turnId/p/:empId`：在同一工作台中钉住一名员工的详情；
- `/s/:turnId` 这一层持有查询结果和三栏布局，换人不重新执行搜索；
- 左栏：服务端分面筛选；
- 中栏：候选表格，一人一行、一个概念词一列；
- 右栏：证据说明或个人时间线；
- `xl` 以下左右两栏使用 Kumo Dialog，宽屏保持非模态常驻栏。

客户端只能从 `src/search/result.ts` 获取运行时值。带数据库连接或密钥的模块都用 `import "@tanstack/react-start/server-only"` 标记自己，页面从它们取值会让构建失败。

## 7. 验收

经历描述可能缺失或被上游抽取截断，因此描述路只作为较弱证据，不能单独代表受控经历。ETL 会报告拒绝导入与无法对齐的数量，但仓库不保存真实统计或查询结果。

工程校验入口是：

```bash
npm run verify
```

检索质量还需一组由业务方确认的 10–20 条找人问题及已知候选人，以建立召回和排序基线。这组题目和答案指向真人，只保存在不进版本库的 `evals/` 下。
