# 人才搜索

面向 HR 与业务负责人的人才搜索工具：按岗位、经验或能力检索员工的组织内任职与入职前工作经历，并查看每项条件的匹配依据。

## 产品目标

在组建团队、内部调配或寻找特定经验时，帮助用户快速形成候选名单，并沿着真实经历判断每位候选人是否合适。

产品回答三个问题：

1. 哪些人具备所需经历；
2. 哪些条件是必须、加分或排除项；
3. 每位候选人的判断依据来自哪段经历、可信度如何。

## 目标用户与场景

- HR：人才盘点、内部推荐、岗位候选初筛；
- 业务负责人：组建团队、补充特定经验、寻找跨领域人才；
- 共同任务：从候选名单进入个人经历，核对匹配依据，而不是只接受一个不可解释的分数。

## 当前范围

### 包含

- 搜索工作台：输入自然语言或关键词，按语义匹配经历，并按序列、职级、经历来源、经历时长、入职前公司、招聘渠道、学历、点名的公司或学校与证据强度收窄；
- 人才库：员工当前信息、公司内任职段与入职前工作经历；
- 可解释匹配：逐项展示命中的经历、时长与证据强度；
- 迭代查询：每个概念词可以设为必须、加分、排除或暂时停用；
- 个人详情：查看职业轨迹、完整时间线和本次查询的匹配依据。

### 不包含

- 权限、多租户和审批流；
- 与 HR 系统实时同步，数据通过离线批次导入；
- 标签治理平台，本项目只消费已经确认的数据来源；
- 无法解释或没有当前读者的派生字段与预留接口。

## 产品原则

- **从经历找人**：检索对象是任职经历，不是抽象画像或人工标签集合；
- **结果必须可解释**：每项条件都能回到具体经历和来源；
- **默认严格，允许调整**：必须词采用 AND 语义，用户可以明确改为加分或排除；
- **计数口径一致**：结果、筛选和分页都以人为单位，并基于同一次检索；
- **不静默降级**：没处放的条件、理解失败、结果截断和数据缺失都必须在界面上说明；
- **只保存当前需要的数据**：每个字段、索引、接口和界面信息都必须有明确读者。

## 核心数据模型

核心人才模型只有两个实体：

- `employee`：一人一行，保存当前展示信息；
- `experience`：一段经历一行，公司内与入职前经历以 `kind` 区分。

岗位名、组织名、序列和经历描述保留可追溯的原始表达，语料里出现过的每一串原文去重成「说法」各存一个向量（`phrase`），经历段按路指向它们（`experience_phrase`）；匹配是查询词先按向量召回说法、再由重排模型判定相关度。

原文四路之外，入职前经历的简历描述由模型读成两类短说法，同样进说法表、同样指回那一段：**能力词**（这段里实际用到或负责的技能、技术、业务领域）和**做过的事**（一个领域加一种参与方式：参与方式只有从零搭建、负责建设、优化改进、参与执行、带队管理五种，判断不出就留空；它只随命中显示、不参与相关度，比相关度的是领域）。它们是对自述的一种读法，不是第二套画像：证据强度与简历原文同档，界面上写明命中的是哪条说法，原文就在旁边供核对。公司内任职段没有自由文本，不抽。不维护同义词表。

能力词是开放词表，同一项能力有多种写法。检索不在乎（它们在向量空间里是邻居），筛选栏「入职前能力」那一栏在乎：它按词数人。所以有一份人维护的对照表（别名 → 标准词，和数据源放在一起、不进版本库），ETL 灌库前按它归并；整理工具把库里相似的能力词圈成组、每组让模型判断哪些只是写法不同，建议追加进对照表，已有的行不动，人改过的就是最终决定。这一栏只覆盖写了简历描述的人：它回答「谁写过」，回答不了「谁不会」。

序列筛选也覆盖入职前经历：每段入职前经历由模型按岗位名、公司名和描述对到公司序列树上的一对一级二级（树取自当前语料里 HR 登记的序列），写在另外两列，人页上标「按岗位名对齐」。对齐只进筛选、不参与打分，登记值和推断值不混在一列；对不上公司任何序列的段（简历里的脏数据、公司没有的业务）就是空，它们不出现在序列筛选里。字段与约束见 [`src/db/schema.ts`](../src/db/schema.ts)。

一次搜索以不可变 `SearchSpec` 保存：`evidence` 是可核对的经历要求，`scope` 是原话中的结构化范围，`notices` 保存未支持条件与太宽的词；分面、翻页和当前查看的人只是 URL 上的临时视图。整句提交先落只有原话的记录，`spec` 由模型在工作台里补上；模型失败则记录停在待理解，界面显示错误与重试。

经历原文只送到嵌入端点与抽取端点（灌库时）和重排端点（查询时）为止，端点放内网还是公网由部署方按数据政策决定。查询理解模型只收到用户那句话和几维筛选的取值，走公网没有顾虑。

## 成功标准

- 用户可以用真实业务问题形成可核对的候选名单；
- 候选人的每项命中都有明确经历依据；
- 收窄筛选不会让结果反向增加，筛选人数与结果总数口径一致；
- 数据异常不会被静默改写成正常经历；
- 页面、命令行和服务端共用同一套查询语义。

落地到一个具体组织时，还需要由业务方提供 10–20 条已知答案的找人问题，用于建立召回与排序验收基线。
这组题目和答案指向真人，只保存在 `evals/` 下、不进版本库；仓库自带的
`evals/sample.json` 是唯一例外——它指向合成样例语料，是干净克隆也能跑通的基线。
