# 人才搜索

面向 HR 与业务负责人的人才搜索工具：按岗位、经验或能力检索员工的组织内任职与入职前工作经历，并查看每项条件的匹配依据。

## 产品目标

在组建团队、内部调配或寻找特定经验时，帮助用户快速形成候选名单，并沿着真实经历判断每位候选人是否合适。

产品回答三个问题：

1. 哪些人具备所需经历；
2. 哪些条件是必须、加分或排除项；
3. 每位候选人的判断依据来自哪段经历、可信度如何。

## 目标用户与场景

- HR：人才盘点、内部推荐、岗位候选初筛；
- 业务负责人：组建团队、补充特定经验、寻找跨领域人才；
- 共同任务：从候选名单进入个人经历，核对匹配依据，而不是只接受一个不可解释的分数。

## 当前范围

### 包含

- 搜索工作台：输入自然语言或关键词，并按序列、入职前公司、经历来源、经历时长与匹配来源收窄；
- 人才库：员工当前信息、公司内任职段与入职前工作经历；
- 可解释匹配：逐项展示命中的经历、时长与证据强度；
- 迭代查询：每个概念词可以设为必须、加分、排除或暂时停用；
- 个人详情：查看职业轨迹、完整时间线和本次查询的匹配依据。

### 不包含

- 权限、多租户和审批流；
- 与 HR 系统实时同步，数据通过离线批次导入；
- 标签治理平台，本项目只消费已经确认的数据来源；
- 无法解释或没有当前读者的派生字段与预留接口。

## 产品原则

- **从经历找人**：检索对象是任职经历，不是抽象画像或人工标签集合；
- **结果必须可解释**：每项条件都能回到具体经历和来源；
- **默认严格，允许调整**：必须词采用 AND 语义，用户可以明确改为加分或排除；
- **计数口径一致**：结果、筛选和分页都以人为单位，并基于同一次检索；
- **不静默降级**：整词退到子串、结果截断和数据缺失都必须在界面或文档中说明；
- **只保存当前需要的数据**：每个字段、索引、接口和界面信息都必须有明确读者。

## 核心数据模型

模型只有两个实体：

- `employee`：一人一行，保存当前展示信息；
- `experience`：一段经历一行，公司内与入职前经历以 `kind` 区分。

岗位名、组织名、序列和经历描述保留可追溯的原始表达。当前匹配直接使用这些字段，不维护另一套派生标签层。字段与约束见 [`src/db/schema.ts`](../src/db/schema.ts)。

## 成功标准

- 用户可以用真实业务问题形成可核对的候选名单；
- 候选人的每项命中都有明确经历依据；
- 收窄筛选不会让结果反向增加，筛选人数与结果总数口径一致；
- 数据异常不会被静默改写成正常经历；
- 页面、命令行和服务端共用同一套查询语义。

落地到一个具体组织时，还需要由业务方提供 10–20 条已知答案的找人问题，用于建立召回与排序验收基线。
这组题目和答案指向真人，只保存在 `evals/` 下、不进版本库；仓库自带的
`evals/sample.json` 是唯一例外——它指向合成样例语料，是干净克隆也能跑通的基线。
